# 나누다컴퍼니 자가출판 서비스 설계

## 목적과 포지셔닝

**핵심 서비스는 조판이다.** 저자가 가진 원고 뭉텅이를 인쇄 가능한 책으로 바꿔주는 것이 우리가 파는 것이고, 실물 인쇄·배송은 그 결과물의 배송 수단이다.

이 포지셔닝의 근거는 시장의 빈 구간이다. 국내 1위 자가출판 플랫폼 부크크조차 **판형별 원고 템플릿을 내려주고 저자가 직접 편집하게** 한다. 유료 표지 디자인은 30만원 이상이고, 교정·교열도 별도 유료 옵션이다. 즉 **"글 → 인쇄용 PDF"** 구간은 여전히 저자의 몫으로 남아 있다.

저자 대부분은 책등 두께를 계산해 305.7×216mm 펼침 표지를 만들 수 없다. 그걸 할 수 있는 사람이면 애초에 우리가 필요 없다. 인쇄용 PDF를 이미 가진 사람을 대상으로 하는 서비스는 사실상 아무도 쓰지 않는다.

1차 범위는 **원고 → 조판 → 표지 → 인쇄 → 배송**이다. ISBN 발급과 온라인 서점 유통은 후속 단계로 분리한다.

## 설계 원칙 (우선순위 순)

1. **최고의 UI/UX가 최우선이다.** 자가출판은 저자에게 감정적으로 큰 행위다. 기존 사이트의 디자인 언어(다크 `#1a1a1a`, 오렌지 `#ff6b35`, 명조 디스플레이, 넉넉한 여백)를 따르고, 각 단계에서 지금 무슨 일이 일어나는지·다음에 무엇을 해야 하는지가 항상 명확해야 한다.
2. **저자가 인쇄 지식을 갖지 않아도 되게 한다.** 도련·책등·제본 여백·페이지 배수 같은 것은 우리가 처리한다. 저자에게는 "작게/보통/크게" 수준의 선택만 남긴다.
3. 외부 제작사·결제사 API에 코드를 직접 결합하지 않는다. 어댑터로 격리한다.
4. 결제·인쇄가 얽힌 경로는 멱등성과 명시적 상태 전이로 보호한다.

## 검증된 사실

### 조판 파이프라인 — 실측 검증 완료

실제 원고(『길에서 만나다』 112,133자)를 조판해 SweetBook 샌드박스에 업로드한 결과 **동기 검증을 통과**했다. 문서상 통과가 아니라 제작사 서버가 실제로 받아준 결과다.

```
pdfSizeMm { width: 154, height: 216 }        ← 규격 정확히 일치
pageMeta  { currentPageCount: 110, isValid: true }
```

| 본문 크기 | 페이지 | 면당 글자 수 |
|---|---|---|
| 작게 | 110p | 1,019자 |
| 보통 | 132p | 849자 |
| 크게 | 160p | 700자 |

- **엔진: pdfkit.** headless Chrome은 조판 품질이 낫지만 크로미움 300MB를 서버리스에 올려야 한다. pdfkit은 UAX#14 줄바꿈으로 한글 조판이 정상 동작하고 Vercel에 그대로 배포된다.
- **폰트: 나눔명조** (SIL OFL 1.1 — 임베딩·재배포 허용).
- 좌우 페이지 여백 비대칭(제본변 18mm / 바깥 14mm), 양쪽 정렬, 페이지 번호 구현됨.

### 한글 전처리 — 품질을 가르는 지점

두 가지를 처리하지 않으면 본문이 망가진다.

1. **줄 합치기.** 한글은 어절 중간에서도 줄바꿈되므로 문단 내 줄을 무조건 공백으로 합치면 `"남자"` + `"가 와 있었다"` → `"남자 가 와 있었다"`로 어절이 깨진다. 양쪽이 한글이고 앞줄이 문장부호로 끝나지 않을 때만 붙인다. PDF·한글문서에서 복사한 원고에 흔한 문제다.
2. **문단 연속 조각.** 페이지를 넘겨 이어지는 조각은 새 문단이 아니므로 들여쓰지 않는다.

**알려진 한계:** 원본 줄바꿈이 어절 경계였는지 중간이었는지는 원리적으로 구분 불가능하다. `"있는 한"` → `"있는한"` 같은 오류가 드물게 남는다. `.docx` 원고는 문단 내 임의 줄바꿈이 적어 실제 영향이 작다.

### 페이지 수 제약이 설계를 지배한다

A5 소프트커버는 **50~200페이지, 2페이지 단위**다. 이것이 조판 엔진과 UX 전체를 규정한다.

- **최소 50p ≈ 3.5만자.** 짧은 에세이집은 미달한다.
- **최대 200p ≈ 17만자.** 장편은 초과한다.
- 일반 에세이 단행본(8~12만자)은 95~170p로 잘 맞는다.

따라서 원고를 올리는 즉시 글자 수로 **예상 페이지와 판형 적합성을 판정**해야 한다(`fitToSpec`). 미달이면 본문 크기를 키워 맞추고, 초과면 줄이거나 분권을 제안한다. 조판 결과가 홀수면 **빈 페이지를 넣어 짝수로 맞추는 것도 우리가 처리**한다. 저자가 알 필요 없는 일이다.

### SweetBook Book Print API

문서 사본은 `docs/vendor/`에 둔다 (루트 도메인이 403을 반환한 전례가 있어 네트워크 의존을 없앴다).

- Base URL: `https://api-sandbox.sweetbook.com/v1` / `https://api.sweetbook.com/v1`. 키와 도메인의 환경이 어긋나면 403 `ERR_ENV_MISMATCH`.
- 인증: `Authorization: Bearer {KEY}`. 결제 모델은 **충전금 선불**.
- 흐름: `POST /books` → `pdf-cover` → `pdf-contents` → `finalization` → `orders/estimate` → `orders`
- 멱등성: `POST /books`·`POST /orders`가 `Idempotency-Key` 지원. 동일 키 + 다른 본문은 422.
- 웹훅 9종, `X-Webhook-Signature`(HMAC-SHA256) 검증. 실패 시 3회 재시도 후 `EXHAUSTED`.
- Rate Limit: 일반 300 req/분, 업로드 200 req/분. 초과 시 429 + `Retry-After`.
- 검증 범위는 **PDF 크기와 페이지 수뿐**이다. 해상도·안전영역·색공간은 검증하지 않는다. **CMYK/PDF-X 요구 없음.**
- 제작 사양: CMYK 4도 오프셋급 디지털 인쇄, PUR 무선제본, 무광 라미네이팅, 1권부터, **제작 5~7 영업일**.

**제작 방식은 `PDF_UPLOAD` 확정.** `TEMPLATE`·`MIX_COVER_TEMPLATE`은 A5 표지 템플릿 8종을 전수 조회한 결과 전부 알림장·일기장·소셜포토북 테마였고, 파라미터가 `childName`·`schoolName`·`coverPhoto` 형태에 제목이 디자인에 고정된 것도 있어 단행본에 쓸 수 없다.

**판형은 A5 소프트커버 기본.** 제품 안내가 A5를 **"단행본 · 매뉴얼 · 일기"** 용도로 명시하고, 4종 중 유일하게 200p를 지원한다. 나머지 3종(A4·스퀘어 HC/SC)도 선택지로 노출한다.

## 사용자 여정

1. **`/publish`** — 서비스 소개, 판형·가격, 제작 과정, 사양 사전 고지.
2. **원고 올리기** — `.docx` / `.md` / `.txt`. 즉시 글자 수를 세어 *"예상 132페이지, A5 제작 가능"* 판정.
3. **책 만들기** — 본문 크기, 장 시작 방식, 판형을 고르면 **조판 결과를 펼침면으로 미리보기**. 옵션을 바꾸면 페이지 수와 가격이 즉시 따라 움직인다.
4. **표지** — 템플릿에 제목·저자명을 넣거나 이미지를 올린다. 책등 두께는 페이지 수에서 자동 계산된다.
5. **확인 → 결제** — 인쇄용 PDF를 내려받거나(디지털), 실물 책을 주문한다.
6. **`/publish/orders/[uid]`** — 상태 타임라인.

핵심은 3번의 **미리보기 → 수정 루프**다. 저자가 "이렇게 나오는구나"를 눈으로 보고 고칠 수 있어야 인쇄 후 클레임이 사라진다.

## 단계 구분

| 단계 | 내용 | 상태 |
|---|---|---|
| **Phase 0** | 인쇄용 PDF 업로드 → 검증 → 견적 → 주문 → 상태 추적 | **구현됨** |
| **Phase 1a** | 조판 엔진 (원고 → 내지 PDF) | **프로토타입 검증됨** |
| **Phase 1b** | `.docx` 파싱, 미리보기 UI, 표지 자동 생성 | 대기 |
| **Phase 2** | 결제 연동, 프로젝트 DB, 저자 계정 | 대기 |
| **Phase 3** | Live 전환, 웹훅 수신 | 대기 |
| **Phase 4** | ISBN, 온라인 서점 유통 | 범위 외 |

Phase 0은 버리지 않는다. **조판 엔진의 출력을 제작사에 넣는 마지막 구간이 이미 검증된 채로 있는 것**이라 그대로 재사용된다.

## 기술 설계

### 아키텍처

```
저자 ─ /publish/* (Next.js, 기존 디자인 시스템)
         │
         └─ app/api/publish/* (Route Handlers, 서버 전용)
                 ├─ lib/publishing/typeset.ts     원고 → 내지 PDF (pdfkit)
                 ├─ lib/publishing/print-guide.ts 표지 도면·기하
                 ├─ lib/publishing/pricing.ts     원가 → 판매가
                 ├─ lib/publishing/sweetbook.ts   제작사 어댑터
                 └─ lib/publishing/payment.ts     결제 어댑터 (신규)
```

키는 서버 환경변수로만 접근한다 (`SWEETBOOK_API_KEY`, `SWEETBOOK_API_BASE`). `NEXT_PUBLIC_` 금지.

### 조판 파이프라인 — 남은 작업

- **`.docx` 파싱** — `mammoth` 등으로 HTML/텍스트 추출 후 기존 `parseManuscript`에 연결. 제목 레벨을 장 구분으로 매핑한다.
- **`.hwp`는 미지원.** 국내 저자 상당수가 한글을 쓰지만 파싱 난도가 높다. *"한글에서 `.docx`로 저장해주세요"* 안내가 현실적이다.
- **비동기 분리** — 100p 이상 조판은 서버리스 실행 시간을 넘길 수 있다. 요청-응답 안에서 처리하지 않는다.
- **미리보기** — 조판 PDF를 페이지 이미지로 렌더해 펼침면으로 보여준다. 전체가 아니라 처음 몇 면 + 지정 페이지만.
- **초기 지원 범위는 순수 텍스트 + 장 구분.** 각주·표·이미지는 범위 밖으로 두고 명시한다.

### 표지 생성

`print-guide.ts`에 기하 계산(재단선·책등·안전영역)이 이미 있다. 여기에 제목·저자명 배치와 이미지 결합을 얹는다.

- 책등 두께는 페이지 수에서 자동 계산되므로 저자가 만질 일이 없다.
- 저자 선택지: 템플릿 + 제목/저자명, 또는 이미지 업로드.
- 도면 SVG는 직접 디자인하려는 저자에게 계속 제공한다 (`/api/publish/cover-guide`).

### 결제 — 어댑터로 격리한다

**결정: 레몬스퀴지 단일 결제로 시작한다.** 디지털·실물 모두 같은 경로로 받는다.

조사 결과 알아둘 사실:

| 사실 | 근거 |
|---|---|
| **모든 MoR이 실물 상품을 금지한다** | Lemon Squeezy·Polar 약관 모두 "Physical products"를 금지 목록 1번에 둔다. 후속 제품인 Stripe Managed Payments도 디지털 전용이다. 예외가 없다 |
| **레몬스퀴지는 유지보수 모드다** | 2024년 Stripe 인수 후 CEO가 "느린 지원 응답, 뜸한 제품 업데이트"를 공식 인정했고, 팀의 역량은 Stripe Managed Payments로 옮겨갔다. **LS 사용자를 그쪽으로 이전시키는 것이 목표**라고 밝혔다 |
| **공식 JS SDK는 정체 상태다** | `@lemonsqueezy/lemonsqueezy.js` v4.0.0, 마지막 배포 2024-11-05 |
| **Wedges는 결제와 무관하다** | 레몬스퀴지가 만든 오픈소스 React UI 라이브러리(Radix + Tailwind, MIT). 우리는 이미 shadcn/ui로 같은 스택을 쓰므로 **도입 이유가 없다** |

우리 상품 구조상 **조판 서비스(인쇄용 PDF·전자책)는 명백한 디지털 상품**이라 MoR로 파는 데 문제가 없다. 문제는 실물 책 부분이다. 위험을 인지한 상태에서 단일 결제로 시작하되, **분리가 언제든 가능한 구조**로 짓는다.

```ts
// lib/publishing/payment.ts
export type LineKind = "digital" | "physical"

export interface PaymentProvider {
  readonly name: string
  createCheckout(input: CheckoutInput): Promise<{ url: string; ref: string }>
  verifyWebhook(raw: string, signature: string): boolean
  parseEvent(raw: string): PaymentEvent
}
```

- 주문 항목에 **`digital` / `physical` 구분을 처음부터 넣는다.** 나중에 실물만 국내 PG로 빼는 것이 설정 변경 수준이 되게 한다.
- SDK는 정체 상태이므로 **REST API를 직접 호출**한다. 어댑터가 한 파일이라 SDK를 쓸 이유가 크지 않고, 유지보수가 멈춘 의존성을 늘리지 않는 편이 낫다.
- 웹훅 서명 검증은 필수. 결제 완료 웹훅을 받은 뒤에만 제작사 주문을 넣는다.
- **전환 트리거를 미리 정해둔다:** 레몬스퀴지가 실물 판매를 문제 삼거나, Stripe Managed Payments 이전이 강제되거나, 실물 매출 비중이 커지면 → 실물 라인을 포트원(국내 PG)으로 옮긴다.

### 상태 모델

Phase 0은 제작사 주문 상태를 그대로 쓴다. 프로젝트 DB를 도입하는 Phase 2의 내부 상태 기계:

```
draft → manuscript_review → typesetting ⇄ proof_ready → quoted → paid
      → print_submitted → (제작사 상태 미러링) → delivered
비정상: rejected(콘텐츠 거절) / cancelled(결제 전 취소)
        / refunded(결제 후 취소·환불) / failed(운영자 개입)
```

- `proof_ready ⇄ typesetting` 역방향 전이(교정 왕복)를 명시한다. 실무에서 가장 자주 밟는 경로다.
- `cancelled`·`refunded`를 정식 상태로 둔다. 전자상거래법상 청약철회 경로가 화이트리스트에 있어야 한다. 제작사 취소는 `PAID`/`PDF_READY`까지만 가능하므로 우리 환불 정책도 "제작확정 전까지"로 정렬한다.

### 데이터 저장

- Phase 0에는 자체 DB가 없다. 상태의 원천은 제작사이며 `externalRef`로 추적한다.
- Phase 2에서 Postgres 도입 (Supabase 또는 Vercel Marketplace 경유 Neon). ~~Vercel Postgres~~는 단종되어 선택지가 아니다.
- 원고·PDF는 **비공개** 버킷에 두고 만료되는 서명 URL로만 접근한다. 원고 본문이 로그·에러 리포트에 남지 않게 한다.
- **알려진 제약:** Vercel Route Handler 본문 한도(~4.5MB). 대용량 파일은 Blob 직접 업로드(presigned)로 우회한다.

## 가격 정책

**중대 주의:** 제작사의 `totalAmount`는 **부가세 제외** 금액이고, 실제 차감액은 `paidCreditAmount = floor(totalAmount × 1.1 / 10) × 10`이다. 초기 구현이 `totalAmount`를 그대로 노출해 **건당 약 10% 역마진** 상태였다(14,627원 표시 / 16,080원 지출). 원가는 반드시 부가세 포함으로 잡는다.

판매가 = 원가(부가세 포함) ÷ (1 − 마진율), 100원 단위 올림. **마진율은 매출 총이익률** 기준이다.

| 수량 | 마진율 | A5 50p 권당 |
|---|---|---|
| 1권 | 40% | 26,800원 |
| 2~4권 | 35% | 22,450원 |
| 5~9권 | 30% | 19,560원 |
| 10~29권 | 25% | 17,860원 |
| 30권~ | 20% | 16,490원 |

- 외부 사례 벤치마크: 고객 29,000원 / 원가 13,860원 = **52% 마진**. 우리 40%는 보수적이며, **초기에는 40%를 유지하고 배송비 조건 협의 후 재검토**한다.
- 같은 사례의 차감액이 단가×1.1과 정확히 일치해 **배송비가 0원**이었다. 우리 계정에는 3,000원(부가세 포함)이 붙는다. 계정별 조건 차이로 보이므로 협의 항목이다.
- 정책은 `lib/publishing/pricing.ts`의 `MARGIN_TIERS` 한 곳에 있다. 검증은 `node lib/publishing/pricing.test.mjs` — 실현 마진이 목표 미만이거나 판매가가 원가 이하면 실패한다.
- **원가·마진율은 클라이언트로 내려보내지 않는다.**
- 조판 서비스(디지털)와 실물 인쇄의 가격을 분리해 표기한다. 디지털만 사고 끝내는 저자에게는 원가가 거의 들지 않는다.

## 클레임 예방

제작사 API는 **PDF 크기와 페이지 수만 검증**한다. 실제 클레임 요인은 검증되지 않고 문서에 권장값도 없다. 조판을 우리가 하면 대부분이 원천 차단된다.

| 요인 | 조판 서비스에서 |
|---|---|
| 표지 크기·책등 오산 | 자동 계산 — 저자가 틀릴 수 없음 |
| 페이지 수 불일치·배수 위반 | 조판 단계에서 강제 |
| 글자 재단 잘림 | 안전영역을 조판 여백으로 보장 |
| 제본변 여백 부족 | 좌우 비대칭 여백으로 처리 |
| 저해상도 이미지 | 저자 업로드 이미지에만 해당 → 표지 업로드 시 경고 |
| 화면색 ≠ 인쇄색 | 사전 고지 + 확인 체크 |

저자가 직접 PDF를 올리는 경로(Phase 0)에는 도면·안전영역 안내·확인 체크리스트를 유지한다. 안전영역 기준은 문서에 없어 우리가 정의했다 — 도련 3mm + 여유 5mm = 가장자리 8mm, 내지 제본변 12mm, 이미지 300dpi (`lib/publishing/print-guide.ts`).

## 서비스 활성화 게이트

결제 연동 전까지 프로덕션에서 신청을 받지 않는다. `PUBLISH_ENABLED=true`로 제어한다 (`lib/publishing/config.ts`).

| 대상 | OFF 동작 |
|---|---|
| `/publish` | "준비중" 배너 + CTA 비활성, `noindex`, sitemap 제외 |
| `/publish/start`, `/publish/orders/*` | 404 |
| `app/api/publish/*` | 503 |

Preview 환경에만 `true`를 넣어 내부 테스트를 계속한다.

## 검증 기준

- `pnpm build` 와 `pnpm check:llms` 가 통과한다.
- 실제 원고로 조판한 PDF가 제작사 동기 검증을 통과한다. **(달성: 110p, 154×216mm, isValid)**
- 조판 결과 페이지 수가 판형 범위·배수 규칙을 항상 만족한다.
- 원고가 판형에 안 맞을 때(과소·과다) 저자에게 이유와 대안이 안내된다.
- 한글 어절이 깨지지 않는다. 문단 연속 조각이 들여쓰기되지 않는다.
- 동일 멱등키로 주문을 재시도해도 주문이 하나만 생성된다.
- 결제 웹훅 서명을 검증하며, 검증 실패 건으로는 제작사 주문이 생성되지 않는다.
- 판매가가 항상 원가를 상회하고 목표 마진을 만족한다.
- 원가·마진율이 클라이언트 응답에 없다.
- `/publish/start`·`/publish/orders/*`가 `noindex`이며 sitemap에 없다.
- API 키가 클라이언트 번들·저장소에 노출되지 않는다.
- 기존 책 상세·리더 라우팅과 SEO 메타데이터가 변경되지 않는다.

## 정책과 법무 (Phase 2 착수 전 확정)

- 원고 저작권은 저자에게 있음을 약관에 명시하고, 이용 목적을 제작 범위로 한정한다.
- 불법 콘텐츠·표절·명예훼손·타인 개인정보 포함 원고에 대한 거절권을 명문화한다 (`rejected` 상태).
- 개인정보처리방침에 원고 파일·배송지 정보의 보관 기간과 위탁(제작사·결제사) 사실을 추가한다.
- 나누다컴퍼니 브랜드로 나가는 책의 최소 품질·내용 기준을 정한다.
- 조판 결과물의 저작권 귀속(우리가 만든 조판·표지 디자인)을 약관에 정리한다.

## 미확인·협의 항목

**SweetBook (Live 전환 전)**

1. 글 위주 단행본 조건 — 200p 초과, 흑백 내지 단가, 본문용 경량 용지. 제품 안내는 용지를 "150~250g/m² 코팅지"라 하는데 API는 내지를 "몽블랑 울트라 화이트 90g"이라 한다. 실물 감촉이 고객 기대와 직결되므로 확인이 필요하다.
2. Live 커스텀 가격·정산 조건, 제작 리드타임, 불량·재인쇄 정책.
3. **배송비 정책** — 계정별로 다를 수 있음.

Live 전환 절차: 사업 협의 → Business 계정 전환 → 파트너 포털에서 Live 키 발급 + 실제 충전금 충전 → 환경변수 교체. 코드 변경은 없다. 충전금은 선불이라 **잔액이 마르면 주문이 402로 막힌다.** 잔액 알림 기준을 정해둔다. 파트너 혜택으로 제작비 지원금 10만원이 안내되어 있다.

**결제**

4. 레몬스퀴지가 KRW 결제·국내 카드를 어떻게 처리하는지 확인 (MoR이라 환율·수수료 구조가 국내 PG와 다르다).
5. Stripe Managed Payments 이전 일정과 강제 여부.

## 후속 옵션

Phase 4에서 유통을 붙일 경우, 나누다컴퍼니가 출판사 자격으로 직접 처리할 수 있다.

- ISBN: 국립중앙도서관 서지정보유통지원시스템에서 책마다 발급. 전산 신청이 가능해 부분 자동화 여지가 있다.
- 서점 등록: 예스24·교보·알라딘 직접 공급계약(전자계약·공동인증서 필요) 또는 유통 총판 1곳 경유. 초기에는 총판 경유가 운영 부담이 적다.
- 서점 상품 등록은 공개 개발자 API 대신 공급사 포털·일괄 업로드 방식일 가능성이 높다. 등록·정산·CS는 사람 운영이 필요한 영역으로 남는다.
